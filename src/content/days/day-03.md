## 1. 反例：所有查询都遍历全部数据

以下是局部反例，不是推荐实现：

```java
List<User> search(String skill) {
    List<User> result = new ArrayList<>();
    for (User user : users.values()) {
        if (user.getSkills().contains(skill)) {
            result.add(user);
        }
    }
    return result;
}
```

数据很小时它完全可用，但需求继续增长后会暴露问题：

- 每个查询都扫描全部用户，单次约 O(n)；
- 名称、技能、排序、分页参数容易堆成超长方法；
- 调用方拿到全部结果再分页，浪费内存和计算；
- 如果技能大小写不统一，查询结果不稳定；
- 为了加速而增加索引后，更新和删除可能忘记同步。

> **必须讲清**：优化不是看到循环就删除循环。先确认查询模式和数据规模，再决定是否建立额外索引；索引用空间和写入成本换读取速度。

查询契约最终定为：

```java
Page<User> search(UserQuery query);
```

Repository 接收一个明确查询对象，返回通用分页结果，不把内部 Map 暴露给调用方。

## 2. 泛型分页模型 `Page<T>`

### 2.1 为什么不是只写 `UserPage`

用户、文章、订单以后都会分页。如果每种类型都重复 items、page、size、totalElements，可以把“元素类型”参数化：

```java
public record Page<T>(
        List<T> items,
        int page,
        int size,
        long totalElements
) { }
```

`T` 是类型参数：

```java
Page<User> users;
Page<String> names;
```

编译器据此限制 items 的元素类型。`Page<User>` 不是运行时装了一个 User 类对象，而是编译期形成明确契约。

### 2.2 构造器保护分页不变量

```java
public Page {
    items = List.copyOf(items);
    if (page < 1) throw new IllegalArgumentException("page 必须 >= 1");
    if (size < 1 || size > 100) {
        throw new IllegalArgumentException("size 必须在 1..100");
    }
}
```

- 页码统一从 1 开始；
- size 限制 1–100，防止一次读取无边界数据；
- `List.copyOf` 创建不可修改浅快照；
- items 中的对象若可变，并不会因此深度不可变。

总页数使用向上取整：

```java
public int totalPages() {
    return totalElements == 0
            ? 0
            : (int) ((totalElements + size - 1) / size);
}
```

例如总数 5、每页 2，结果是 3 页。

### 2.3 泛型不变性

**故意错误示例，不能编译：**

```java
List<String> names = new ArrayList<>();
// List<Object> values = names;
```

如果允许赋值，就能通过 `values.add(1)` 把 Integer 放入字符串列表。即使 String 是 Object 的子类型，`List<String>` 也不是 `List<Object>` 的子类型。

只读打印未知元素可使用：

```java
static void printPage(Page<?> page) {
    for (Object item : page.items()) {
        System.out.println(item);
    }
}
```

`Page<?>` 表示元素类型未知；可以安全读取为 Object，但不能随意写入未知类型。

> **容易被问**：泛型擦除后还有什么价值？类型错误已经在编译期被阻止，并减少业务代码的强制转换；擦除只说明部分类型参数运行时不可直接判断。

## 3. 查询模型 `UserQuery`

```java
public record UserQuery(
        String nameContains,
        Set<String> skills,
        UserSort sort,
        int page,
        int size
) { }
```

本案例固定语义：

| 字段 | 语义 |
|---|---|
| `nameContains` | 忽略大小写的包含查询；null 等同空字符串 |
| `skills` | 用户必须同时拥有全部技能；null 等同空集合 |
| `sort` | null 默认 `ID_ASC` |
| `page` | 从 1 开始 |
| `size` | 1–100 |

紧凑构造器负责规范化：

```java
nameContains = nameContains == null
        ? ""
        : nameContains.trim().toLowerCase(Locale.ROOT);
```

技能查询也统一 trim、转小写、去重。领域对象仍保留展示形式，例如 `TypeScript`；索引 Key 使用 `typescript`。展示值与查询 Key 可以有不同规范。

为什么不用五个散落参数？

- 参数顺序不容易传错；
- 查询语义集中；
- 后续增加条件不会让接口无限增长；
- 校验与默认值有统一入口。

## 4. List、Set、Map 在查询中的不同职责

```text
Map<Long, User> users
    主存储：ID → User

Map<String, LinkedHashSet<Long>> skillIndex
    倒排索引：规范化技能 → 用户 ID 集合

List<User> matches
    最终候选的排序列表

Set<Long> candidates
    多个技能索引求交集时的候选 ID
```

### 4.1 为什么索引保存 ID，不直接保存 User

如果索引和主 Map 都保存 User，更新时可能出现两份对象引用和版本不一致。索引只保存稳定 ID，最终从主存储取当前 User：

```java
User user = users.get(id);
```

### 4.2 多技能“全部匹配”就是集合交集

```java
candidates.retainAll(ids);
```

查询 `Java + Spring` 时：

```text
Java  → {1, 2, 4, 5}
Spring→ {4}
交集   → {4}
```

`retainAll` 会修改当前 candidates，因此必须先复制第一份索引集合，不能直接修改索引本身。

**故意错误示例：**

```java
Set<Long> candidates = skillIndex.get("java");
candidates.retainAll(skillIndex.get("spring"));
```

这会把 `java` 索引永久缩小，破坏后续查询。

### 4.3 快照、视图和内部集合

- `List.copyOf(users.values())` 返回不可修改快照；
- `Collections.unmodifiableList(original)` 通常是不可修改视图，original 变化仍可见；
- `subList` 是原列表的范围视图，因此 Page 构造器再次 `List.copyOf`；
- Repository 不能返回 `skillIndex` 或内部 Map。

## 5. Comparator 与稳定排序

排序枚举：

```java
public enum UserSort {
    ID_ASC, ID_DESC, NAME_ASC, NAME_DESC
}
```

名称升序：

```java
Comparator<User> byId = Comparator.comparing(User::getId);
Comparator<User> byName = Comparator
        .comparing(User::getName, String.CASE_INSENSITIVE_ORDER)
        .thenComparing(byId);
```

`thenComparing(byId)` 是稳定结果的业务保证：两个名称比较结果相同时，继续按 ID 排序。不能依赖 HashMap 遍历顺序或某次 JVM 的偶然结果。

降序不能盲目写错 tie-breaker。需要明确：名称降序后，相同名称仍按 ID 升序。完整实现将比较器规则集中在 Repository 私有方法中。

### 5.1 Comparator 与 Comparable

- Comparable 是类型自己的自然顺序；
- Comparator 是外部提供的一种排序策略；
- User 同时需要 ID、名称等多种排序，更适合 Comparator；
- 不要为了一个页面排序就强迫 User 只有唯一自然顺序。

### 5.2 排序与分页顺序不能颠倒

正确流程：

```text
筛选 → 排序 → 计算总数 → 截取当前页
```

如果先截取再排序，只能保证当前小片段有序，无法得到全局第 N 页。

## 6. 倒排索引与一致性

### 6.1 新增或更新

```java
User previous = users.put(saved.getId(), saved);
if (previous != null) {
    removeFromIndex(previous);
}
addToIndex(saved);
```

更新必须先移除旧技能，再加入新技能。否则用户删除 Java 技能后仍会出现在 Java 查询中。

### 6.2 删除

```java
User removed = users.remove(id);
if (removed == null) return false;
removeFromIndex(removed);
return true;
```

当某技能的 ID 集合为空时，同时删除空索引 Key，避免长期留下无意义条目。

### 6.3 复杂度与成本

| 操作 | 无索引 | 有技能索引后的直觉 |
|---|---|---|
| 按技能找候选 | 扫描全部用户 O(n) | 平均接近读取对应 ID 集合 |
| 创建/更新 | 主 Map 写入 | 还要维护每个技能索引 |
| 删除 | 主 Map 删除 | 还要从所有旧技能集合移除 ID |
| 内存 | 只存主数据 | 额外保存技能到 ID 的映射 |

Big-O 描述增长趋势，不是精确毫秒。真实数据库索引还涉及 B-Tree、统计信息、磁盘和查询优化器，今天的内存倒排索引只是建立“以空间和写成本换查询速度”的模型。

> **必须讲清**：索引一致性属于 Repository 实现职责，Service 不应同时操作主 Map 和索引 Map。

## 7. 完整查询调用链

```java
UserQuery query = new UserQuery(
        "",
        Set.of("java"),
        UserSort.NAME_ASC,
        1,
        2
);
Page<User> page = service.search(query);
```

```text
App 创建 UserQuery
  → UserQuery 构造器规范化和校验
  → UserService.search
  → UserRepository.search 契约
  → InMemoryUserRepository.search
      读取技能索引候选 ID
      按名称二次过滤
      Comparator 全量排序
      记录 totalElements
      计算 from/to
      创建 Page<User> 不可修改快照
  → 返回 App
```

分页截取：

```java
int from = (int) Math.min(
        (long) (query.page() - 1) * query.size(),
        matches.size()
);
int to = Math.min(from + query.size(), matches.size());
```

使用 long 参与乘法，避免页码与 size 相乘先发生 int 溢出。页码超出范围时返回空 items，同时保留真实 totalElements 和 totalPages。

### 7.1 预期输出

```text
Java 第1页: [1:Alice[Java, TypeScript], 2:Bob[Java, Vue]]
总数/总页数: 4/2
Java 第2页: [4:David[Java, Spring], 5:Eve[Java, Python]]
Cara 加 Java 后总数: 5
删除 Alice 后总数: 4
分页校验: page 必须 >= 1
```

> **现场演示**：在 `search`、`removeFromIndex`、`addToIndex` 设置断点，观察 Cara 更新前后 Java 索引以及删除 Alice 后的变化。

### Q03. `List<String>` 是 `List<Object>` 子类型吗？

**面试官提问**

> `List<String>` 是 `List<Object>` 子类型吗？

### Q24. 内存索引能代替数据库索引吗？

**面试官提问**

> 内存索引能代替数据库索引吗？

**候选人回答（可直接口述）**

不能直接代替。Day3 的技能倒排索引是进程内的 Map，它帮助我理解“用额外空间和写入维护成本换查询速度”的思想，但它只服务当前进程，程序重启后会丢失，也没有数据库的事务、并发控制、持久化、执行计划和崩溃恢复能力。

**结合当天项目**

当前 Map<String, LinkedHashSet<Long>> 让“Java 技能 → 用户 ID 集合”查询更快，保存和删除时同步维护；它适合单进程教学和小数据，不负责跨进程一致性。

**原理与边界**

数据库索引由存储引擎维护，通常涉及 B+ 树、哈希或其他结构，并受事务和优化器管理。内存索引、缓存、数据库索引与搜索引擎倒排索引解决的问题相近但运行边界不同。

**常见错误回答**

> “有了 HashMap 查询就是 O(1)，所以数据库不需要建索引。”

**一句话收尾**

package com.example.day3;
import java.util.ArrayList;
import java.util.Comparator;
import java.util.LinkedHashMap;
import java.util.LinkedHashSet;
import java.util.List;
import java.util.Locale;
import java.util.Map;
import java.util.Optional;
import java.util.Set;
public final class InMemoryUserRepository implements UserRepository {
    private final Map<Long,User> users=new LinkedHashMap<>();
    private final Map<String,LinkedHashSet<Long>> skillIndex=new LinkedHashMap<>();
    private long nextId=1;
    @Override public User save(User user){ User saved=user.getId()==null?user.withId(nextId++):user; User previous=users.put(saved.getId(),saved); if(previous!=null) removeFromIndex(previous); addToIndex(saved); if(saved.getId()>=nextId) nextId=saved.getId()+1; return saved; }
    @Override public Optional<User> findById(Long id){return Optional.ofNullable(users.get(id));}
    @Override public List<User> findAll(){return List.copyOf(users.values());}
    @Override public boolean existsByEmail(String email,Long excludedId){for(User user:users.values()) if(user.getEmail().equalsIgnoreCase(email)&&!user.getId().equals(excludedId)) return true; return false;}
    @Override public boolean deleteById(Long id){User removed=users.remove(id); if(removed==null)return false; removeFromIndex(removed); return true;}
    @Override public Page<User> search(UserQuery query){
        Set<Long> candidates=null;
        for(String skill:query.skills()){ Set<Long> ids=skillIndex.getOrDefault(skill,new LinkedHashSet<>()); if(candidates==null)candidates=new LinkedHashSet<>(ids); else candidates.retainAll(ids); }
        if(candidates==null)candidates=new LinkedHashSet<>(users.keySet());
        List<User> matches=new ArrayList<>();
        for(Long id:candidates){User user=users.get(id); if(user!=null&&user.getName().toLowerCase(Locale.ROOT).contains(query.nameContains()))matches.add(user);}
        matches.sort(comparator(query.sort()));
        int from=(int)Math.min((long)(query.page()-1)*query.size(),matches.size()); int to=Math.min(from+query.size(),matches.size());
        return new Page<>(matches.subList(from,to),query.page(),query.size(),matches.size());
    }
    private Comparator<User> comparator(UserSort sort){ Comparator<User> byId=Comparator.comparing(User::getId); Comparator<User> byName=Comparator.comparing(User::getName,String.CASE_INSENSITIVE_ORDER); return switch(sort){case ID_ASC->byId;case ID_DESC->byId.reversed();case NAME_ASC->byName.thenComparing(byId);case NAME_DESC->byName.reversed().thenComparing(byId);}; }
    private void addToIndex(User user){for(String skill:user.getSkills())skillIndex.computeIfAbsent(key(skill),ignored->new LinkedHashSet<>()).add(user.getId());}
    private void removeFromIndex(User user){for(String skill:user.getSkills()){String key=key(skill); LinkedHashSet<Long> ids=skillIndex.get(key); if(ids!=null){ids.remove(user.getId());if(ids.isEmpty())skillIndex.remove(key);}}}
    private String key(String skill){return skill.trim().toLowerCase(Locale.ROOT);}
}
